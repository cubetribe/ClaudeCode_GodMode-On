## governance-core
HOW: The repo-root CLAUDE.md is the compact orchestrator law: on any request the session classifies the request type, reads and increments VERSION, creates reports/vX.X.X/, announces the version, checks MCP servers, classifies risk (Smart Routing default vs Full-Gates escalation), and then delegates to a fixed linear agent chain (inline arch brief or @architect → @builder → @validator ∥ @tester → @scribe), where each agent drops a numbered report into the version folder and returns a 3-line STATUS verdict. Deeper rules live in 13 skills and docs/orchestrator/* loaded on demand. templates/CLAUDE-ORCHESTRATOR.md is the long-form variant of the same law intended for projects; config/CLAUDE-system.md and config/CLAUDE-projekt.md are older templates for the global and project CLAUDE.md layers; config/claude-settings.json wires enforcement hooks (API-impact check on Write/Edit, agent-output validation on SubagentStop/TaskCompleted/TeammateIdle). Installation via scripts/apply-global-claude-setup.sh copies agents, scripts, and skills into ~/.claude and copies the ROOT CLAUDE.md to ~/.claude/templates/CLAUDE-ORCHESTRATOR.md — it never installs a global ~/.claude/CLAUDE.md, never installs the config/ templates or settings file, and the repo's own 499-line templates/CLAUDE-ORCHESTRATOR.md is never deployed. Orchestration is strictly SINGLE-TASK-oriented: one user request maps to exactly one version bump, one report folder, and one workflow run, and there is no plan, sprint, backlog, or multi-task artifact anywhere in the governance core. Which of the four CLAUDE-style files is authoritative for orchestrator behavior is documented nowhere; in practice the root CLAUDE.md is authoritative because the installer ships it, but the user's live ~/.claude/CLAUDE.md is maintained manually and can drift (it currently reflects v8.0.0 content while the repo says v8.0.1).

- claude-settings.json denies writes to .env*/*.pem/*.key and validates agent output at multiple lifecycle events.

## agents-core
HOW: The core agents form a fixed pipeline the Orchestrator drives: (researcher) -> architect -> api-guardian (if API/type files touched) -> builder -> validator + tester (+ security when sensitive) in parallel -> scribe -> github-manager. Each agent has a persona file defining role, tool list, "What I DO NOT Do" boundaries, an on-screen output banner, an on-disk report path under reports/v[VERSION]/NN-<agent>-report.md, and a compact verdict (STATUS + max 3 findings + report path) returned to the Orchestrator. ## skills-routing
HOW: Routing is a two-tier decision made by the Orchestrator per request. Smart Routing (cost-efficiency) is the default: it maps work type to a minimal agent set (e.g. docs-only → @scribe only, simple bug → @builder + targeted @validator) and replaces @architect with a 3–5 bullet inline brief for small/medium tasks. Six risk signals (API/type paths, security surfaces, VERSION/CHANGELOG, user-facing UI, new modules, breaking changes) force escalation to Full-Gates (workflows skill), which prescribes fixed agent sequences per command pattern, always ending in the parallel @validator ∥ @tester gate defined in quality-gates with a mandatory decision matrix and max 3 retry cycles. A keyword-driven meta-decision layer (analyze-prompt.js) can further adapt the workflow, e.g. emergencyHotfix strips gates down to @builder → @validator, and documentationOnly skips @builder. ## skills-release
HOW: The release subsystem is built on a Version-First doctrine: before any work, the Orchestrator reads the single-line VERSION file (declared the single source of truth), decides MAJOR/MINOR/PATCH per the semver table, creates reports/vX.X.X/, and announces the target version. VERSIONING.md additionally instructs creating a CHANGELOG entry for the planned changes before work starts. All agents then write numbered reports (00-researcher through 06-scribe) into the gitignored reports/vX.X.X/ folder and return a compact STATUS verdict to the Orchestrator per QUALITY-GATES.md. Any change touching VERSION or CHANGELOG.md is itself a Full-Gates risk signal per WORKFLOWS.md/MODES.md, forcing the full @architect -> @builder -> @validator∥@tester -> @scribe path. Breaking API changes add @api-guardian and mandate a MAJOR bump with @scribe documenting the break in CHANGELOG. At completion, CLAUDE.md's Start step 8 says @scribe updates VERSION + CHANGELOG, while skills/release says @scribe merely verifies VERSION/CHANGELOG/docs/reports and @github-manager then creates the release branch/PR, tags after merge, and publishes a GitHub Release with the CHANGELOG excerpt. Before any push, a 7-item (skills/release) or 5-item (VERSIONING.md) checklist must pass, including both gates APPROVED, no duplicate CHANGELOG version, and explicit user push permission, with the absolute rule that the same version is never pushed twice. Tooling support exists (version-bump.js to bump, sync-version.js to align version strings, pre-push-check.js to block incomplete pushes), though the docs only name version-bump.js. There are no rules at all for pre-releases, RCs, or pre-release tags, and no rule verifying that the tag/GitHub-Release step actually happened.
### strengths
- Version-First discipline (read VERSION, decide bump, create reports/vX.X.X/, announce) gives every unit of work a stable version-scoped workspace and audit trail.
- The pre-push checklist plus 'NEVER push the same version twice' and 'explicit user permission' rules form a clear, memorable push gate.
- Touching VERSION/CHANGELOG.md is itself a Full-Gates risk signal, so release artifacts cannot be edited through the minimal Smart Routing path.
- The breaking-change protocol cleanly chains classification (@api-guardian) -> approval (@architect) -> consumer updates (@builder) -> CHANGELOG documentation (@scribe) -> mandatory MAJOR bump.
- Separation of duties in the release workflow (@scribe verifies, @github-manager executes branch/PR/tag/release) is a sound two-role design.
- The semver decision table with concrete framework-specific examples (new agent=MINOR, docs=PATCH) removes most bump-classification ambiguity.
- QUALITY-GATES.md's return-verdict contract (STATUS + max 3 findings + report path) with script-enforced report min-lengths is a precise, machine-checkable interface.

## scripts
HOW: The scripts directory is meant to be the deterministic enforcement layer under the prompt-based orchestration. apply-global-claude-setup.sh mirrors agents, scripts, and skills into ~/.claude, and config/claude-settings.json (or the plugin manifest) wires four hooks: session-start.js greets each session, validates the framework VERSION, creates reports/vX/, and shows a resume banner if .ccgm-state.json exists; analyze-prompt.js classifies each user prompt and hard-blocks premature-push or gate-skip requests; check-api-impact.js warns on API/type file writes and mandates @api-guardian; validate-agent-output.js checks every finished subagent report for required sections/patterns and blocks @scribe if gates are not APPROVED. workflow-state.js is the intended single source of workflow truth (stage, agents completed/pending, dual gate status, push approval) persisted in .ccgm-state.json so sessions can resume across /compact and so pre-push-check.js can refuse a git push until the workflow is complete, gates approved, and VERSION/CHANGELOG updated. The release lifecycle is version-bump.js (increment VERSION, insert CHANGELOG template, create report folder) plus sync-version.js (propagate the version into CLAUDE.md and prompt files), while check-update.js/auto-update.js compare the installed ~/.claude against GitHub and can self-update with backup and rollback. In practice, the chain is broken in the middle: no hook or agent ever writes .ccgm-state.json, the hook wiring passes no/wrong arguments to validate-agent-output.js and check-api-impact.js (Claude Code delivers hook input as stdin JSON, which no script reads), and parallel-quality-gates.js only simulates the gates. So the enforcement layer degrades to session-start cosmetics plus manually invoked CLI utilities, and the real gating remains purely prompt-level.

## version-sweep
HOW: The VERSION file at repo root is declared the single source of truth (docs/orchestrator/VERSIONING.md). Per Core Rule 1 (version-first), the orchestrator reads VERSION and increments it BEFORE any work starts, creates a matching CHANGELOG entry and a gitignored reports/vX.X.X/ folder, and all agent reports land there. scripts/version-bump.js automates exactly that trio (VERSION + CHANGELOG template + report folder) with a CHANGELOG-uniqueness guard. ## public-docs
HOW: The public docs form an install-and-use funnel: README and QUICK_START point to docs/INSTALLATION.md, whose primary path is running scripts/apply-global-claude-setup.sh (or .ps1) to mirror the repo's agents, scripts, skills, and two templates into ~/.claude, with the five CCGM prompts as a paste-into-Claude fallback that additionally configures hooks, config, and the prompt library. Per project, the user copies ~/.claude/templates/CLAUDE-ORCHESTRATOR.md to ./CLAUDE.md, which Claude Code auto-loads as the Orchestrator. Each session the user runs /model best and /effort ultracode (session-scoped) and then types 'GodMode: <request>'; the orchestrator classifies the request, bumps VERSION first, creates reports/vX.X.X/, and routes through Smart Routing or Full-Gates workflows. Agents write full reports to reports/vX.X.X/NN-<agent>-report.md and return a 3-bullet STATUS verdict; @validator and @tester run in parallel and both must approve before @scribe updates VERSION/CHANGELOG and @github-manager opens PRs (never pushing without permission). The policy docs (CONTEXT_SCOPE, SECURITY_TOOLING, RARE_MATRIX) define per-agent scope, tool access, and accountability; REPORT_TEMPLATES defines report shapes enforced by validate-agent-output.js; workflow-state.schema.json backs scripts/workflow-state.js, which persists a single .ccgm-state.json in the project cwd to survive /compact. Updates flow through CCGM_Prompt_98 (auto-update.js with backup/lock/rollback) or re-running the setup script, and CCGM_Prompt_99 restores the orchestrator identity after context loss. AGENT_ARCHITECTURE.md explains the source-vs-runtime dual-location model that all of this rests on: repo files are the versioned source, ~/.claude is what Claude actually loads, and changes only take effect after an install step copies them over.
### strengths

- The 15-agent roster and its 8+1+6 breakdown match exactly across README, docs/AGENTS.md, docs/ARCHITECTURE.md, docs/AGENT_MODEL_SELECTION.md, CLAUDE.md, and both install prompts.
- The verdict contract (STATUS APPROVED/BLOCKED/DONE, max 3 findings, report path, orchestrator opens full report only on BLOCKED) is a crisp, uniform interface defined in REPORT_TEMPLATES.md and repeated verbatim in CLAUDE.md.
- CONTEXT_SCOPE_POLICY's explicit handoff sections, escalation format, and per-agent context budgets are exactly the ownership primitives a sprint-based redesign can build on.
- SECURITY_TOOLING_POLICY's single-writer rule (only @scribe may write VERSION/CHANGELOG/README, only @builder writes src/) is a strong existing guard against parallel overwrites.
- apply-global-claude-setup.sh is genuinely idempotent with timestamped backups, a .cc-godmode-version marker, a --check verification mode, and an honest closing note about what it does NOT do.
- The CHANGELOG is high quality — Keep-a-Changelog + SemVer, per-release rationale prose, explicit Migration sections, and the 8.0.1 entry even documents its own version-sweep methodology.
- README's documentation index cleanly layers Guides / Reference / Policies, and docs/AGENTS.md explicitly declares itself the human-facing roster deferring to docs/orchestrator/AGENTS.md as the machine registry.

### risks_parallel
- reports/vX.X.X/ is keyed only by version with fixed NN-agent-report.md filenames, so two parallel workflows or sprints under the same version silently overwrite each other's architect/builder/gate reports.
- Version-First mandates incrementing VERSION before any work starts, so parallel sessions each bump the same VERSION file with no reservation, lock, or per-sprint version-relevance rule documented anywhere.
- VERSION, CHANGELOG.md, and README version boxes are single files with a single owner (@scribe) and no merge/ordering protocol, making every concurrent sprint's release step a write conflict.
- workflow-state.js persists exactly one .ccgm-state.json in process.cwd() with one required sessionId, so two concurrent sessions in the same project clobber each other's workflow stage, gate status, and pushApproved flag.
- The shared global ~/.claude runtime can be rewritten by the setup script or auto-update while other sessions are mid-workflow; only auto-update has a lock (~/.claude/.update-lock), the setup script has none.
- Ownership in CONTEXT_SCOPE/SECURITY_TOOLING is per-agent-role, not per-session or per-sprint — nothing in the public docs assigns file scopes to a workflow instance, which is precisely the 'no overwrites' gap the maintainer wants to close.
- The dual-gate decision matrix and SYNC POINT semantics assume exactly one builder→gates pipeline; no doc defines gate behavior when multiple @builder subagents run in parallel or when re-runs regenerate the same 03-/04- report files.
- The docs themselves are a conflict surface: the version string lives in 10+ files (VERSION, plugin.json, CLAUDE.md, template, README, QUICK_START, five prompt headers/banners), so parallel doc-editing agents without explicit file ownership will collide on every release, as the manual 8.0.1 sweep demonstrates.
